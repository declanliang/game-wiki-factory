# 新游戏上站提示词流程（阶段 b：发给 AI 逐步执行）

这份文档是 `npm run launch:site` 的**分步骤、人工可插入检查点**的版本——同样的流程，一条命令能跑完，但如果想在每个阶段之间自己看一眼结果再继续，就按这份文档把 Part 0-5 的提示词依次发给 AI，每个 Part 之间自己验证一遍再发下一个。两种方式最终都要跑通 [README.md](../README.md) 的「上线前验收」才算完成。

> **这份文档只覆盖阶段 b（发提示词给 AI 执行）。准备素材、clone 新目录这些人类操作在 [doc/上线准备手册.md](上线准备手册.md)（阶段 a）——先做完那份手册的检查表，再回来发下面的 Part 0。**

> **如果 `intake/site-content.json` 是交给独立的内容生成工具（比如 seoscout）产出的**，直接把 [doc/homepage-info-schema.md](homepage-info-schema.md) 最上面那段可复制的 Prompt 原文喂给它，不要套用任何其他模板/课程材料的字段格式——那些跟当前这套模板的结构对不上，照那个格式产出的数据不会生效。

每个 Part 的提示词原文可以直接复制粘贴，不需要手动替换任何变量——所有变量都从 `intake/` 里按约定路径读取。

## 阶段 b：执行（发给 AI 的提示词，按顺序、逐个验证）

### Part 0：上下文加载

**每次开新对话（不管是不是同一个 AI）第一条消息都发这个**，确保 AI 不需要任何历史记忆就能接手：

```
你现在负责把这个游戏 Wiki 模板套用到一个新游戏上线。这是一个已经从纯净模板 clone 出来的项目，
当前工作目录就是项目根目录，后面所有路径都是相对这个目录的相对路径。

请先做三件事：
1. 读 README.md，了解整体规则和验收标准
2. 读 doc/新游戏上站提示词流程.md，了解接下来 Part 1-5 要做什么
3. 读 intake/site-identity.json（身份字段的标准来源；如果不存在，看 new-site.env 有没有覆盖值——
   两者都没有 GAME_NAME/OFFICIAL_GAME_URL 说明阶段 a 的准备工作还没做完，停下来告诉我，不要继续）

跑 npm run check:intake 和 npm run validate:articles，确认都是 0 error（这两个脚本校验
intake/ 素材是否齐全、文章结构是否有问题，有 error 说明阶段 a 还没做完，停下来告诉我，
不要自己猜着往下走）。

读完用几句话跟我确认：这次要上线的是什么游戏、文章素材在哪、有没有可选项被跳过（比如没提供 YOUTUBE_VIDEO_ID）。
确认无误我再发 Part 1。
```

### Part 1：基础配置

**目标**：favicon、Hero 图、manifest.json、站点身份（`site.*`）换成新游戏的。主题色不用改——`src/app/globals.css` 里的 `--nav-theme`/`--nav-theme-light` 是固定值，所有站点统一使用，不是每个游戏的可配置项（原因见 README「素材」一节），不要为了这次上线去改这 4 行。

```
这一步是纯机械字段搬运，不需要手写——直接跑两个脚本：

npm run apply:content    # 站点身份（site.*）+ 首页文案（intake/site-content.json，如果存在）
npm run process:assets   # hero 图 / favicon 全套 / manifest.json

它们会自动读 intake/site-identity.json（或 new-site.env 覆盖值）拿 GAME_NAME/OFFICIAL_GAME_URL/
YOUTUBE_VIDEO_ID 等身份字段，自动按约定路径（intake/hero/、intake/favicon/ 等，见 README「素材」
一节）找 hero 图和 favicon 素材——两者都没提供也不会报错，process:assets 会自动用游戏名首字母
生成一套图标顶上。跑完看终端输出确认每一项是 ✓ 还是 warn/info，warn/info 的条目按提示核实一下是不是
符合预期（比如"没有 hero 图"是不是真的没有素材，还是路径放错了）。

不需要手动改 src/locales/en.json 的 site.* 或 public/ 下任何文件——脚本已经处理完了。
主题色不用管——src/app/globals.css 的 --nav-theme/--nav-theme-light 是固定值，不是这次上线要改的东西。

⚠️ 不要修改 home.* 里除了 hero.videoId 之外的其他字段（这个也已经被 apply:content 自动填了）——
   那些归 Part 2。
⚠️ 不要动 src/config/navigation.ts、content/ 目录——那些归 Part 3。

## 验证方法
grep -c "$(读 intake/site-identity.json 的 GAME_NAME)" src/locales/en.json
file public/images/hero.webp public/android-chrome-512x512.png
grep -rn "__[A-Z_]*__" src/locales/en.json public/manifest.json
# 最后一条：确认这一步该填的占位符（site.* 相关）都替换掉了，没替换的会以 __XXX__ 形式原样留在文件里
```

### Part 2：首页内容

**目标**：把首页 `home.*`（除 Part 1 已处理的 `hero.title`/`description`/`videoId` 外）换成新游戏文案。照着 JSON 结构填数据就行，不碰 `HomePageClient.tsx` 组件代码。

```
参考 intake/site-content.json（固定约定路径；老项目用嵌套的 intake/homepage-info/site-content.json 也一样会被找到，新项目不要新建这个子目录）。

更新 src/locales/en.json 的 home 命名空间：

1. home.hero：eyebrow/title/description/stats[]（{value, label} 对象数组，固定展示前 4 个，
   超过 4 个会被截断，建议放"热度类"数字如访问量/更新时间/服务器人数——value 放数字/短语，
   label 放说明文字，不要拼成一个字符串再指望组件去拆）/primaryCta+Href（必须指向导航页如 /guide，
   不要指向具体文章）/secondaryCta+Href（一般是官方游戏地址，跟 site.playUrl 同一个值）

2. home.aboutGame：title/paragraphs[]（可以用 **关键词** 高亮游戏名/开发商等重点词）/
   stats[]（label+value 的事实规格类信息：开发商/平台/类型等，不要跟 hero.stats 填重复的数字）/cta+ctaHref

3. home.featured：title/viewAllHref/viewAllLabel/items[]
   —— items 先留空数组 []，不要在这一步编具体条目。这个模块的选文交给 Part 3 按固定规则
   自动生成（规则需要真实的 category/date 数据，这一步文章还没接入 content/，编不出真实数据）。
   intake/featured-override.json 里如果明确写了指定的候选文章，Part 3 会优先采用；没写就完全走
   自动规则，不需要你或用户在这一步做任何选择、也不需要为了"填满这个字段"瞎编占位内容。

4. home.liveTools（可选）：兑换码/梯度榜/服务器状态这类时效性内容才需要，
   没有就把这个 key 从 JSON 里整个删掉（不要留一个空对象或空 items 数组），
   首页会自动跳过这个区块，不会留空标题。

5. home.extraSections（可选，数组）：角色/职业/道具/异常这类"条目式"内容才需要——
   跟 liveTools 不是一回事，liveTools 是时效性内容，extraSections 是不随时间过期的
   分类条目展示，目的是把具体条目名摆到首页提升关键词密度。只给内容量足够（每类 4 条以上）
   的分类做一块，没有就整个不写这个 key。items[].href 这一步先留空数组（跟 featured 一样，
   等 Part 3 文章接入之后才有真实文章路径可填）。

6. home.faq：title/description/items[]（question/answer，问答里要带游戏名）。
   answer 支持内嵌一种链接语法 [链接文字](/分类/slug)，自然能带链接就带，不强制每条都有。

7. home.finalCta：title/description/primary+Href/secondary+Href

⚠️ 不要修改 home.categories（分类导航卡片区完全自动生成，零配置）、home.updates（同样自动从文章读取）。
⚠️ 不要修改 site.*、footer.*——那些已经在 Part 1 处理。

## 验证方法
python3 -c "import json; json.load(open('src/locales/en.json'))"
grep -rn "__[A-Z_]*__" src/locales/en.json
# 应该只剩 Part 3 之前故意占位的文章 href（如果有），其他占位符应该已清零
npx tsc --noEmit
```

### Part 3：内容与导航分类

**目标**：把文章接入 `content/`，注册对应的导航分类，让首页 `featured`/`liveTools`/`extraSections` 里占位的 href 指向真实文章。

```
处理 intake/articles 里的 .mdx 文章（固定约定路径，除非 new-site.env 显式覆盖了 ARTICLES_DIR）。
结构性问题（metadata 完整性、重复 slug、异常大文件）应该已经被 Part 0 跑的 validate:articles
挡住了；这里只做内容质量判断，脚本判断不了。

## 接入前先做内容质量扫描（不要跳过）
1. 文不对题检查：标题/正文有没有把游戏机制词当成字面意思的现实概念来写（比如游戏里的
   "Nurse" 职业被写成了真实护士职业介绍）
   grep -l -iE "real-world|real life|virtual and real|game and reality" $ARTICLES_DIR/**/*.mdx
2. 汇总发现向我汇报，我确认要排除哪些之后再继续，不要自己默默排除或全盘接入。
   删除整篇文章一定要先问我。

## 接入
1. 把确认收录的文章挪到 content/<locale>/<category>/<slug>.mdx
   （category 文件夹名就是分类 slug，全小写，跟下面的 navigation.ts key 一致；
   locale 看 ARTICLES_DIR 下实际有哪些 <locale>/ 子目录，第一次通常只有 en）
2. 跑 npm run sync:categories 自动注册新分类到导航栏/侧边栏/列表页
3. 跑 npm run check:config，0 error/0 warning 才算过
4. 生成 home.featured.items[]：跑 npm run generate:featured（不需要手动执行这套规则，
   脚本已经实现了）——固定规则：按 NAVIGATION_CONFIG 的分类顺序遍历，每个有文章的分类选 1 篇，
   优先选标题/slug 命中 beginner/getting-started/how-to-play/guide/start/intro 这类入门关键词的
   文章，命中不了就选该分类里 metadata.date 最新的一篇；选够的分类数不足 4 个时允许同一分类补选
   第 2 篇，直到总数达到 4 篇或耗尽；总数上限 8 篇。确定性算法，同一批文章任何时候重跑结果一致。
   如果有明确想指定的候选文章，不用等这一步——在 intake/featured-override.json 放一份
   [{"category": "guide", "slug": "xxx"}, ...] 结构化清单，脚本检测到就直接用它，不跑算法。
5. 如果 Part 2 里 home.liveTools / home.extraSections 有内容（占位 href 指向 /guide），
   换成本次真实收录的文章/工具页路径——这两块本身放什么内容不是从文章列表能自动推出来的，
   仍然以 intake/site-content.json 里提供的为准，这一步只是补真实链接。extraSections 每一项的
   href 必须精确对应真实存在的文章路径（跟 check:config 的死链扫描对上），不能是编的。

⚠️ 如果这次没有文章（homepage-only 模式），允许 content/ 保持空——不要生成假文章、不要因为没有文章就卡住。
   这种情况下 home.featured.items 就先留空数组，等文章生成后再补。

## 验证方法
npm run check:config
find content -name '*.mdx' | wc -l
grep -rn "__[A-Z_]*__" src/locales/en.json
```

### Part 4：多语言完整性

**目标**：验证完整性契约，合并固定五语言的译文。

```
确认 ARTICLES_DIR 下有 en/es/de/fr/ja 五个目录，并与 site-plan 一致。

1. 用 npm run sync:locales 自动同步语言配置
   （前提：先在 content/<locale>/ 建好翻译文章目录，脚本会以 content/ 下实际存在的语言目录为准，
   自动注册进 routing.ts / request.ts / language-switcher.tsx 三处）
2. 确认每个非英文语言都有对应的 intake/site-content.<locale>.json（比如 intake/site-content.es.json，
   跟 intake/site-content.json 同一套 schema，只是值已经是目标语言）—— 这份文件不是这一步产出的，
   应该在阶段 a 准备 intake/ 素材时就已经跟文章一起交付了；缺了就停下来问我要，不要自己用 LLM
   现翻一份顶上，这个模板本身不做翻译。
3. 跑 npm run apply:locales，把每个语言的 intake/site-content.<locale>.json 机械合并进
   src/locales/<locale>.json（跟 apply:content 对 en.json 做的是同一套合并逻辑，纯搬运，
   不是生成式步骤）——某个语言缺文件、或者结构跟英文版对不上，会直接报错退出，报错信息里会点名
   具体缺什么/哪里对不上。
4. 翻译 content/<locale>/ 下的全部文章。文章树、可见 UI、分类描述或法律页缺少译文时必须失败；禁止在非英语 URL 静默显示英语正文。

## 验证方法
npm run check:config
for f in src/locales/*.json; do python3 -c "import json; json.load(open('$f'))" && echo OK: $f || echo BAD: $f; done
grep "locales:" src/i18n/routing.ts
```

### Part 5：全站验证与收尾

**目标**：确认站点没有残留占位符、类型检查/构建/内链检查全部通过、sitemap 里每个 URL 都能访问、部署域名已经设置成真实值。

```
执行全站验证：跑 npm run verify:site，一次性做完占位符扫描 → tsc → check:config →
生产构建 → 起服务检查 sitemap loc/hreflang 全部直接 200、每页 self-canonical、og:image/twitter:image/hreflang，不需要逐条手动跑。
有 error 直接定位到对应 content/ 文件或 en.json 字段修复，重新跑，不需要凭感觉判断"应该修好了"。

部署前额外跑一遍 npm run verify:deploy——在 verify:site 基础上，确认 NEXT_PUBLIC_SITE_URL（裸域名会规范为 HTTPS origin）并检查线上 title、canonical、og:url、图片 URL、sitemap/robots 与全部 hreflang 目标；3xx 或 metadata 缺失都视为失败。
已经设置为真实部署域名（不是 src/config/site.ts 里的占位域名），并直接访问线上域名确认能打开。
这个变量写在 .env.local 或部署平台（比如 Vercel）的环境变量设置里，new-site.env 里不需要
（也没有）域名字段，本地开发全程不需要域名。

全部通过后，可以删除 intake/ 和 new-site.env（已经在 .gitignore 里，不影响提交，删不删都行）。

## 验证方法（同上，本 Part 本身就是验证）
npm run verify:site
npm run verify:deploy
```

## 修改这份文档时的固定格式

每个 Part 遵循同一个骨架：**目标 → 参照（数据从哪来）→ 修改（改哪些文件/字段）→ ⚠️ 硬约束/Part 分工边界 → 验证命令**。缺任何一环 AI 都容易跑偏——没有参照会瞎编内容，没有边界会越界改了别的 Part 该管的字段，没有验证会漏改。

变量不写在提示词文本里手动替换，全部从 `intake/` 按约定路径读取——提示词原文本身固定不变，AI 自己读配置文件取值。这份文档跟脚本改动应该保持同步：改了某个 `npm run xxx` 脚本的行为，对应 Part 里引用它的地方也要跟着改，不要让提示词描述的行为和脚本实际行为对不上。
