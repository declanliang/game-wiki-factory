# 游戏基础配置自动化：目标、结论与联网搜索方案

> 状态：方案调研阶段，暂不编写实现代码  
> 更新时间：2026-07-16

## 1. 项目目标

把游戏 Wiki 首页资料准备中的第一段流程自动化：

```text
输入游戏名称（推荐同时提供游戏平台和官方页面）
→ 联网搜索游戏基础资料
→ 识别并验证来源
→ 提取结构化事实
→ 生成网站首页所需配置
→ 输出来源与质量检查报告
```

第一阶段只处理“输入游戏名称 → 搜索基础信息”，暂不处理文章关键词挖掘和文章生成。

## 2. 首页基础信息的范围

目标数据包括：

- 游戏身份：正式名称、游戏平台、开发者、发行日期、类型。
- 官方入口：官网、游戏商店页、Discord、Reddit、YouTube、官方 Trailer。
- 游戏事实：核心玩法、特色机制、访问量、收藏量、在线人数、等级上限、角色或技能数量等。
- 动态信息：最近更新、有效兑换码及奖励。
- 首页内容：Hero、Start Here、About Game、Final CTA、Footer 和共享文案。
- SEO 配置：title、description、keywords。
- 视觉和市场建议：主题色、深浅色模式、多语言优先级、favicon 提示词。
- 首页模块：最多八个有真实需求和资料支撑的内容模块。

其中“事实采集”和“营销文案生成”必须分开。模型只能根据已经采集到的事实写文案，不能用文案补齐不存在的数据。

## 3. 自动化可行性结论

工程流程可以做到接近完全自动化，但不能把“自动完成”理解为“所有结果必然正确”。

- 搜索、网页读取、链接检查、信息提取、JSON 生成和格式校验可以自动完成。
- 资料不足、同名游戏、来源冲突、动态数据过期时，应进入异常状态，不能强行生成。
- 每项重要事实应保存来源 URL、采集时间、来源类型和置信度。
- 普通结果可自动通过；低置信度结果进入人工审核队列。

推荐输入不只是游戏名称，而是：

```text
游戏名称：必填
游戏平台：推荐
官方商店页或官方游戏页：强烈推荐
目标市场：可选
```

官方页面可以解决同名游戏、拼写差异和错误平台匹配问题。

## 4. ToAPIs GPT-5.5 调研

指定文档：<https://docs.toapis.com/docs/cn/api-reference/chat/gpt-5.5/chat>

该页面明确展示了：

- OpenAI Chat Completions 兼容格式；
- 多轮对话和 system/user/assistant 消息；
- 流式输出；
- 图片输入；
- temperature、top_p、max_tokens 等常规生成参数。

但在当前指定页面中，没有发现以下联网搜索能力的接口定义：

- `web_search` 或类似工具；
- `tools` / `tool_choice` 搜索调用；
- 搜索域名、地区、时间范围过滤；
- `citations` 或 `search_results` 返回字段；
- 由服务端明确保证的实时网页检索。

因此，当前结论是：**不能根据这份文档认定 ToAPIs 的 `gpt-5.5` 接口支持联网搜索。** 它目前更适合承担“把已采集资料分析、归纳并生成结构化配置”的工作，而不是独立承担资料搜索。

另外，ToAPIs 是 OpenAI 兼容 API 网关，其页面中的模型命名和能力应以该服务商的实际说明与测试结果为准，不能仅因为模型名称中含有 GPT，就推定具备某种官方工具能力。

后续如果考虑使用它，需要向服务商确认：

1. 是否存在未写在该页面中的联网搜索模型或接口；
2. 是否返回可机器读取的引用 URL；
3. 是否支持 JSON Schema/严格结构化输出；
4. 是否有数据保留、并发、限流和失败重试说明；
5. 用同一问题实际测试时，能否查到刚刚发布的页面并返回真实来源。

在这些问题确认前，不把 ToAPIs 作为搜索层。

## 5. Perplexity API 调研

指定文档：<https://docs.perplexity.ai/docs/getting-started/overview>

Perplexity 官方文档明确提供多种联网能力：

### 5.1 Search API

- 返回实时、排序后的原始网页搜索结果；
- 支持域名、语言和地区等过滤；
- 适合程序自己控制搜索结果、来源筛选和后续采集；
- 它主要返回搜索结果，不负责生成完整的首页配置。

文档：<https://docs.perplexity.ai/docs/search/quickstart>

### 5.2 Sonar API

- 提供内置联网搜索的 AI 回答；
- 返回 `citations` 和 `search_results`；
- 支持搜索选项、流式输出等能力；
- API 格式与 OpenAI 客户端较容易衔接；
- Sonar Pro 更适合需要多来源和复杂判断的查询。

文档：<https://docs.perplexity.ai/docs/sonar/quickstart>

接口返回结构：<https://docs.perplexity.ai/api-reference/sonar-post>

### 5.3 Agent API

- 可以组合模型与 `web_search`、`fetch_url` 等工具；
- 更适合“先搜索、再打开具体网页、再综合分析”的多步骤任务；
- 灵活性较高，但流程、成本和模型自主行为也更复杂。

### 5.4 成本概况

Perplexity 当前分别按搜索请求、模型 token、搜索上下文或工具调用计费，具体价格可能调整，实施前应再次读取官方价格页：

<https://docs.perplexity.ai/docs/getting-started/pricing>

对本项目而言，普通 Sonar 查询的单次成本较低；但如果每个游戏拆成很多查询、使用高搜索上下文或 Deep Research，批量运行成本会明显增加。因此需要缓存搜索结果，并避免对稳定信息反复搜索。

## 6. 三种候选方案

### 方案 A：Perplexity Sonar 一次完成搜索和整理

```text
游戏名称 → Sonar/Sonar Pro → 带引用的结构化结果
```

优点：

- 接入简单；
- 天生联网；
- 有引用和搜索结果；
- 适合快速验证产品方向。

缺点：

- 搜索、取证和文案生成耦合在一次调用中；
- 一个引用未必精确支撑输出中的每个字段；
- 对动态数据、来源优先级和冲突处理的控制有限。

适用：第一版原型和少量游戏测试。

### 方案 B：Perplexity Search/Agent 负责采集，LLM 负责整理

```text
游戏名称
→ Search API 搜索候选来源
→ 来源筛选
→ fetch_url/网页提取
→ 事实抽取与冲突处理
→ GPT/其他 LLM 生成首页配置
```

优点：

- 每一步可检查、可缓存、可重试；
- 能建立字段级来源；
- 可以明确优先使用官网、平台 API、官方社交账号；
- 将来容易替换搜索或生成服务。

缺点：

- 系统设计比方案 A 多几个步骤；
- API 调用次数更多；
- 需要定义来源评分、冲突处理和缓存规则。

适用：正式批量生产。**这是当前推荐的长期方案。**

### 方案 C：由 Codex 直接执行每个游戏的调研

优点：

- 当前就能联网查找、分析文档和检查结果；
- 适合和用户一起迭代字段、提示词与质量标准；
- 不必马上建设完整后台。

缺点：

- 更像开发和运营工作流，不是稳定的后台 API；
- 不适合作为网站长期无人值守运行的唯一依赖；
- 大批量重复执行、定时更新和成本核算不如专用程序明确。

适用：现在的需求澄清、样本测试、结果抽查和自动化系统开发。

## 7. 当前推荐路线

分两个阶段推进：

### 阶段一：用样本验证数据规范

暂时由 Codex 或 Perplexity Sonar 对少量不同类型游戏进行搜索，验证：

- 哪些字段稳定可获得；
- 哪些字段只能从特定游戏平台 API 获得；
- 哪些字段经常冲突；
- 引用能否真正证明对应事实；
- 最终首页 JSON 应采用什么结构。

此阶段重点是确定输入、输出和判定规则，不急着写完整程序。

### 阶段二：建设正式自动化管线

采用“搜索/采集层 + 事实层 + 生成层”分层设计：

```text
输入层
  游戏名称、平台、官方 URL

搜索与采集层
  平台官方 API → 官方网页 → 官方社媒 → 权威媒体 → 社区来源

事实层
  去重、来源评分、冲突处理、采集时间、置信度

生成层
  首页文案、SEO、模块规划、主题与语言建议

验证层
  JSON Schema、字符长度、链接状态、必填字段、禁止编造
```

搜索服务优先考虑 Perplexity；生成模型保持可替换，ToAPIs 只有在进一步确认能力和稳定性后再决定是否使用。

## 8. 数据质量原则

1. 来源优先级：平台官方 API > 官方网站/商店页 > 官方公告/社媒 > 权威媒体 > 高质量社区。
2. 官方来源不存在时才使用社区来源，并明确标记。
3. 不允许为了满足模板数量而编造数据。
4. 动态字段必须保存 `retrievedAt`。
5. 冲突事实不自动选一个看起来合理的答案，应按来源和时间处理或进入审核。
6. 链接可访问不等于内容可信，两项需要分别判断。
7. 首页展示数据与内部证据数据分离，前台 JSON 可以简洁，后台必须可追溯。
8. 首页模块应为“最多八个”，而不是资料不足时强制凑满八个。

## 9. 下一步需要解决的问题

在写代码前，建议按顺序完成：

1. 确定第一版需要采集的字段清单；
2. 设计最终输出 JSON，以及内部来源/置信度结构；
3. 选择 3 个不同平台、不同资料丰富度的样本游戏；
4. 用 Perplexity/Codex 实际搜索并记录缺失与冲突；
5. 决定第一版采用 Sonar 快速原型，还是直接采用分层采集方案；
6. 再开始编写自动化程序。

## 10. 当前结论摘要

- ToAPIs 指定的 GPT-5.5 文档没有证明其支持联网搜索，不建议目前把它作为搜索层。
- Perplexity 明确支持联网搜索、引用和搜索结果返回，适合本项目。
- 快速原型可以使用 Sonar/Sonar Pro。
- 正式批量系统建议把搜索采集与 LLM 整理分开。
- Codex 很适合先帮助完成样本调研、数据结构设计和质量规则验证。
- 当前最重要的下一步不是选模型，而是先确定第一版的字段结构与证据结构。

## 11. 第二轮调研：ChatGPT、OpenRouter 与 Perplexity Agent API

> 调研日期：2026-07-16。本节反映当前文档状态，相关服务可能继续调整。

### 11.1 为什么 ChatGPT 网页版能搜索，但普通模型 API 页面看不到搜索

“模型”和“产品工具”是两个层次：

- GPT 模型负责理解、推理和生成；
- ChatGPT 网页版在模型之外提供网页搜索、文件、图片等产品工具；
- API 是否能搜索，取决于调用入口是否把 `web_search` 工具暴露出来，而不只是模型名称。

因此，ChatGPT 网页版具有“Web search”，不代表任意第三方的 `/chat/completions` 兼容接口都会自动拥有相同工具。

OpenAI 官方 API 当前确实提供网页搜索工具。官方文档说明，可以在 Responses API 的 `tools` 中启用 `web_search`，并获得带来源引用的最新网页信息：

<https://developers.openai.com/api/docs/guides/tools-web-search>

这也修正了第一轮结论需要强调的边界：不是“GPT API 本身都不支持搜索”，而是 **ToAPIs 指定的 GPT-5.5 Chat Completions 页面没有证明其网关暴露了搜索工具**。

### 11.2 OpenRouter 的 GPT-5.5 能否联网

模型页面：<https://openrouter.ai/openai/gpt-5.5>

OpenRouter 可以给 GPT-5.5 增加联网搜索。不过搜索能力来自 OpenRouter 的工具层或底层提供商，并不是只写模型 slug 就天然发生搜索。

OpenRouter 当前推荐使用：

```text
tools: [{ type: "openrouter:web_search" }]
```

官方说明：<https://openrouter.ai/docs/guides/features/server-tools/web-search>

这个服务端工具具有以下特点：

- 模型决定是否搜索以及搜索几次；
- 可选 `auto`、原生提供商搜索、Exa、Firecrawl、Parallel 或 Perplexity 搜索引擎；
- 可控制域名、搜索上下文和总结果数量；
- 返回标准化 URL 引用；
- 可以用于没有原生搜索能力的模型，必要时由 OpenRouter 接入外部搜索引擎。

旧的 `:online` 模型后缀和 `plugins: [{ id: "web" }]` 方式已经被 OpenRouter 文档标为弃用，新项目不应以旧方式为主。

因此：**OpenRouter + GPT-5.5 可以满足联网搜索，但应把它理解为“GPT-5.5 + OpenRouter 搜索工具”，而不是单独 GPT-5.5 的固有能力。**

需要注意：

- `openrouter:web_search` 当前仍标记为 Beta；
- `auto` 可能随模型和提供商选择不同搜索引擎；
- 如果追求结果可复现，应明确指定搜索引擎、模型和参数；
- 仍要测试引用是否精确支撑每一个输出字段。

### 11.3 Perplexity 应选择哪个 API 模式

Perplexity 当前文档已经把 Sonar API 标为 maintenance mode，并建议新集成默认采用 Agent API：

<https://docs.perplexity.ai/docs/sonar/quickstart>

因此本项目不再建议从 Sonar 开始，优先评估：

```text
Perplexity Agent API
+ web_search
+ fetch_url
+ JSON Schema structured output
```

Agent API 文档：<https://docs.perplexity.ai/docs/agent-api/quickstart>

它适合当前需求的原因：

- `web_search` 用于发现官网、商店页、官方社媒和其他资料；
- `fetch_url` 用于读取搜索发现的具体页面，而不只依赖摘要；
- 搜索结果包含稳定 ID、URL、标题、摘要、发布日期和更新时间；
- 可以要求正文使用 `[1]` 形式引用结果 ID；
- `response_format: json_schema` 可以约束最终输出结构；
- 支持域名和时间过滤；
- 可以调用不同厂商的模型，无须分别管理这些模型提供商的 Key。

### 11.4 Perplexity Agent 的模式选择建议

Agent API 提供动态预设：

- `fast-search`：一步搜索，适合单个简单事实；
- `pro-search`：中等搜索深度，最多约三步，并具有 `web_search`、`fetch_url`；
- `deep-research`：更高搜索深度和最多约十步；
- `advanced-deep-research`：最大研究深度，成本和延迟更高。

预设文档：<https://docs.perplexity.ai/docs/agent-api/presets>

当前需求不是单一问题，而是一次采集多个字段、识别官方来源并处理冲突。因此：

- `fast-search` 太浅，不适合作为完整游戏资料采集模式；
- `pro-search` 最适合作为第一轮样本测试；
- `deep-research` 可作为资料复杂、同名冲突或来源不足时的升级路径；
- `advanced-deep-research` 暂时没有必要。

这不是最终架构决定。样本测试时应比较两种 Perplexity 用法：

1. 动态 `pro-search` 预设：配置少，便于验证效果；
2. 显式固定模型、`web_search`、`fetch_url`、步骤数和 token 预算：结果更可复现，适合以后生产。

动态预设的底层模型、系统提示词和配置会由 Perplexity 更新。如果正式生产要求回归测试和稳定结果，应在验证完成后冻结配置。

### 11.5 搜索与结构化输出不要强行只做一次调用

虽然 Agent API 能同时搜索和返回 JSON Schema，但第一版测试建议保留两个逻辑阶段：

```text
阶段 A：搜索、打开页面、返回候选事实和来源
阶段 B：根据候选事实生成网站首页结构
```

原因是“满足 JSON Schema”只能证明结构正确，不能证明事实正确。阶段 A 应保存原始 `search_results`；阶段 B 的每个重要事实应指向阶段 A 的来源 ID。

### 11.6 当前环境状态

检查时，工作区磁盘上的 `.env` 文件大小为 0 字节，没有读取到任何环境变量。可能是 IDE 中的修改尚未保存。调研阶段没有发起任何 Perplexity API 调用，也没有读取或显示任何密钥。

## 12. 还需要调研的其他 API

Perplexity/OpenRouter 解决的是通用搜索和分析，但某些首页数据更适合从权威结构化接口获得。建议按以下优先级补充文档。

### 第一优先级：游戏平台官方数据

需要先确定准备支持哪些平台：

- Roblox：游戏详情、开发者、访问量、收藏数、当前玩家等官方接口文档；
- Steam：商店详情、开发商、发行日期、类型、评价等接口文档；
- 其他平台：PlayStation、Xbox、Epic、itch.io 或游戏官网的公开接口。

如果第一版只支持 Roblox，应先只研究 Roblox，不需要同时铺开所有平台。

### 第二优先级：YouTube 官方数据

需要 YouTube Data API 文档，用于：

- 识别官方频道；
- 搜索 Trailer；
- 获取视频标题、频道、发布日期、播放量；
- 避免依赖网页搜索模型猜测哪个视频最合适。

### 第三优先级：网页正文提取与反爬降级

Perplexity 的 `fetch_url` 可以先用于原型。如果测试发现网页正文不完整，再比较：

- Firecrawl；
- Jina Reader；
- Exa Contents；
- 自建普通 HTTP + HTML 正文提取。

这一类暂时不必提前购买，先通过样本测试确认是否真的缺失。

### 第四优先级：搜索结果交叉验证

仅当 Perplexity 搜索覆盖率不够或需要供应商备份时，再调研：

- Google Programmable Search 或 Serper；
- Brave Search API；
- Exa；
- Tavily。

不建议一开始同时接入多个通用搜索 API，会增加成本和冲突处理复杂度。

### 暂不属于第一阶段

以下能力以后需要，但不阻塞“输入游戏名 → 搜索基础信息”：

- Google Trends/关键词搜索量 API：用于多语言和 SEO 优先级；
- 图片生成 API：用于 favicon；
- 图片颜色提取：可以本地处理，不必购买 API；
- Discord API：内部服务器内容通常需要 Bot 权限，第一阶段只验证公开邀请链接；
- Reddit API：可用于社区观点，但不应作为官方事实的首选来源。

## 13. 希望用户下一步提供的资料

暂时不需要继续寻找更多通用 LLM API。更有价值的是提供：

1. 第一版目标游戏平台，尤其是否先只做 Roblox；
2. 对应游戏平台的官方或可信 API 文档；
3. 如果已有 OpenRouter Key 或计划采用 OpenRouter，再提供其账号侧搜索工具/费用配置相关文档即可，不需要提供 Key 本身；
4. 选择 2-3 个样本游戏：一个资料丰富、一个新游戏、一个容易同名或资料较少的游戏。

拿到这些信息后，再进行无代码的字段可获得性测试设计，然后才决定最终接口组合。

## 14. 第一版平台范围：仅支持 Roblox

第一版明确只支持 Roblox。这样输入可以收敛为：

```text
必填：Roblox 游戏名称或 Roblox 游戏页面 URL
推荐：直接提供 Roblox 游戏页面 URL
```

如果输入 URL，系统应先从 URL 取得 `placeId`，再解析对应 `universeId`。Roblox 多数公开游戏详情接口使用的是 `universeId`，不能把两种 ID 混为一谈。

## 15. Roblox Engine API 与 Cloud API 的职责

### 15.1 Engine API 不作为本站采集主接口

文档：<https://create.roblox.com/docs/reference/engine>

Engine API 主要记录 Roblox Experience 内部使用的类、服务、属性、事件和 Luau 接口，用于编写游戏本身的逻辑。它不适合充当外部 Wiki 服务的公开游戏资料搜索接口。

对当前项目而言，它只在以下特殊情况下才可能有用：

- 我们拥有目标游戏，并愿意在游戏内增加脚本主动上报等级上限、职业数、Boss 数等自定义数据；
- 将来开发一个供游戏开发者安装的 Roblox 插件或上报组件。

当前要采集的是其他公开 Roblox 游戏，因此第一版不依赖 Engine API。

### 15.2 Cloud API 和公开 Roblox REST 端点是权威数据层

文档：<https://create.roblox.com/docs/cloud>

Roblox Cloud 文档同时列出了稳定 Open Cloud 端点和部分传统 Roblox Web API。它们可用于自动化工具和 Web 应用。

与首页基础信息最相关的能力包括：

- Universes：游戏/Experience 基础信息；
- `games.roblox.com/v1/games`：公开游戏详情；
- Favorites Count：收藏数；
- Votes：投票信息；
- Thumbnails：游戏图标和缩略图；
- Groups/Users：开发者或开发组资料；
- Localization：官方支持语言、本地化名称和描述；
- Badges：徽章，可辅助判断游戏机制，但不等于完整玩法资料。

Universes 参考：<https://create.roblox.com/docs/cloud/reference/features/universes>

Thumbnails 参考：<https://create.roblox.com/docs/cloud/reference/features/thumbnails>

Roblox 官方建议生产环境尽可能使用支持 API Key 或 OAuth 2.0 的稳定 Open Cloud 端点。传统 Cookie 端点稳定性较低，不应使用账号 Cookie 建设采集系统。

同时，Cloud 目录中有一些明确标为 `None`、无需登录的公开读取端点，例如游戏详情、收藏数、投票、公开本地化信息等。这些端点可能对我们的第三方 Wiki 数据采集很有价值，但正式采用前需要做稳定性、限流和字段验证。

### 15.3 Roblox API 能直接提供与不能提供的数据

可以优先从 Roblox 获得：

- 正式游戏名和官方描述；
- 创建者/开发组；
- Roblox 游戏页面；
- 创建、更新时间；
- 当前在线人数、累计访问量、收藏量等公开统计字段（以具体端点实测字段为准）；
- 图标和缩略图；
- 官方支持语言和本地化名称/描述；
- Badge 等平台内公开资源。

通常无法仅靠 Roblox 平台接口可靠获得：

- 等级上限；
- 职业、种族、角色、技能、武器和 Boss 的完整数量；
- 当前有效兑换码；
- 新手攻略和 Tier List；
- 官方 Discord、Reddit 和 YouTube Trailer 的完整对应关系；
- 玩家最关心的八个 Wiki 模块。

这些仍需要联网搜索、官方社媒/公告和网页内容提取。

## 16. DataForSEO YouTube SERP API 评估

文档：<https://dataforseo.com/apis/serp-api/youtube-serp-api>

它适合承担 YouTube 搜索层，可按关键词、地区和语言返回 YouTube 搜索结果，并提供视频详情、描述、时长等数据。文档还列出 Video Info、字幕和评论等独立能力。

对当前首页采集最适合的用途：

- 搜索“游戏名 trailer”“游戏名 official trailer”；
- 获取候选视频及其排名、频道、描述、时间等信息；
- 当没有官方 Trailer 时，寻找高热度玩法视频；
- 后续关键词阶段分析玩家关注的视频主题。

它的限制是：

- 排名靠前不等于官方；
- 播放量高不等于适合嵌入 Wiki；
- 仍需结合频道身份、描述中的官方链接和 Roblox 游戏身份做验证；
- 它不负责采集 Roblox 游戏事实。

当前价格页显示三种执行方式：

- Standard Queue：约 `$0.0006`/SERP 页，通常需要排队；
- Priority Queue：约 `$0.0012`/SERP 页；
- Live Mode：约 `$0.002`/SERP 页，平均最长约 6 秒。

价格会变化，实施前需再次查官方价格。我们的流程不是交互式搜索页面，第一版批处理可以优先考虑便宜的 Standard Queue；只有即时预览才需要 Live Mode。

当前结论：**值得保留，但不是第一条必须接通的 API。** Perplexity 能先完成 Trailer 候选搜索；只有其 YouTube 覆盖和结构化字段不稳定时，再接入 DataForSEO。后续文章关键词挖掘阶段，DataForSEO 的价值会明显提高。

## 17. Jina Reader 评估

文档：<https://jina.ai/reader/>

Jina Reader 通过在目标 URL 前添加 `https://r.jina.ai/`，将网页转换为适合 LLM 读取的 Markdown/文本。它也支持 PDF、浏览器渲染、图片描述，以及通过 ReaderLM-v2 按 JSON Schema 提取字段。

适合当前项目的用途：

- 读取游戏官网、公告、更新日志和帮助页面；
- 清理页面导航、广告和无关布局；
- 给 LLM 提供更稳定、长度更可控的正文；
- 当 Perplexity `fetch_url` 提取失败或内容过短时作为降级方案；
- 保存原始采集文本，便于追踪和重新生成。

重要限制：

- 它是网页读取器，不负责发现 URL；
- 不会绕过站点访问控制或反爬限制；
- 返回原始语言，不负责翻译；
- 网页正文能读取不代表来源可信；
- 不应用它重复读取已经能从 Roblox JSON API 获得的结构化字段。

文档当前显示无 Key 基础调用约为 20 RPM；带免费 Key 的额度更高。第一版样本测试甚至可以不提供 Jina Key，确认确实需要后再决定。

当前结论：**Jina Reader 很适合作为独立的网页提取降级层，但不应该替代 Perplexity 搜索或 Roblox API。**

## 18. Roblox 第一版数据源职责

```text
输入 Roblox URL/游戏名
          │
          ├─ Roblox 官方接口
          │    身份、universeId、名称、描述、开发者、统计、图片、语言
          │
          ├─ Perplexity Agent pro-search
          │    官网/社媒/公告/Discord/Reddit/攻略事实的发现与交叉验证
          │
          ├─ Jina Reader（按需降级）
          │    打开并清洗已发现的网页正文
          │
          ├─ DataForSEO YouTube（暂时可选）
          │    Trailer、官方频道和热门视频候选
          │
          └─ LLM 结构化整理
               事实归并、来源映射、首页 JSON 和质量报告
```

优先顺序是：Roblox 结构化事实优先于网页搜索结果；官方页面优先于社区；无法确认的字段留空或进入审核。

## 19. 当前仍缺少的 Roblox 关键确认

在写代码之前，还需要通过少量真实样本确认：

1. 从普通 Roblox 游戏 URL 稳定解析 `placeId → universeId` 的最佳官方端点；
2. `games.roblox.com/v1/games` 当前实际返回哪些统计字段；
3. 无认证公开端点的限流和批量上限；
4. Open Cloud API Key 能否读取非本人拥有的公开 Universe，以及所需权限范围；
5. 缩略图接口支持的尺寸、格式和返回状态；
6. Roblox 官方描述中外链被过滤后，如何识别 Discord/YouTube 等官方账号；
7. 动态统计数据的缓存时间和更新频率。

下一步适合选择三个 Roblox 样本游戏，设计一张“目标字段—首选来源—降级来源—是否动态—验证规则”矩阵。完成这张矩阵后再进行只读 API 实测。

## 20. Perplexity 与 Roblox 两个样本的实际测试

> 测试日期：2026-07-16。模型输入中只提供游戏名称；用户提供的 Roblox URL 只用于事后验证。

样本：

- Anime Expeditions，验证 URL：`https://www.roblox.com/games/84515722934860/Anime-Expeditions`
- PursuitCore，验证 URL：`https://www.roblox.com/games/121903154323395/PURSUITCORE`

### 20.1 Perplexity `pro-search`

第一次使用动态 `pro-search` 搜索 Anime Expeditions，客户端等待 180 秒后超时，没有取得最终结果。

这说明 `pro-search` 虽然研究深度更高，但把它直接作为每个游戏的一次性默认调用可能带来明显延迟。超时是否仍产生服务端费用，需要以后通过 Perplexity 用量记录确认。

### 20.2 Perplexity `fast-search`

`fast-search` 每个样本只调用一次搜索工具，单次约 7-8 秒：

- Anime Expeditions：约 `$0.01108`；
- PursuitCore：约 `$0.01078`。

实际效果：

#### Anime Expeditions

成功找到：

- 官方 Trailer 候选；
- Discord：`discord.gg/animeexpeditions`；
- 游戏类型和若干玩法资料。

但没有找到验证用的 Roblox 游戏页面，因此没有得到 Place ID、Universe ID、开发组和 Roblox 统计信息。搜索结果还包含第三方 Wiki 和攻略站。

结论：只依赖一次通用 Web Search，对刚上线或尚未充分被搜索引擎索引的 Roblox 游戏会漏掉关键身份。

#### PursuitCore

成功准确找到用户提供的 Roblox 页面：

```text
https://www.roblox.com/games/121903154323395/PURSUITCORE
```

正确得到 Place ID，并发现另一个同名 PURSUITCORE Place，主动提示冲突，没有直接把二者混为一谈。但它没有取得 Universe ID、开发组和完整统计。

结论：通用搜索对已被索引的游戏表现不错，但不能稳定替代 Roblox 结构化接口。

### 20.3 Roblox 无 Key 公开接口验证

通过公开 Roblox 读取端点，两个样本均可自动完成：

```text
placeId → universeId → 游戏详情/统计
```

Anime Expeditions：

- Place ID：`84515722934860`
- Universe ID：`7613921865`
- 当前名称：`Anime Expeditions [TIME CHAMBER]`
- 开发组：`Expeditions Entertainment`
- 类型：Strategy / Tower Defense
- Max Players：24
- 可获得 `playing`、`visits`、`favoritedCount`、`created`、`updated` 等动态字段

PursuitCore：

- Place ID：`121903154323395`
- Universe ID：`10428543942`
- 当前名称：`PURSUITCORE [replay]`
- 开发组：`TamaCorp`
- Max Players：8
- 同样可取得公开动态统计和时间字段

动态数字没有写成长期结论，因为它们会持续变化；系统应在每次采集时保存数值和 `retrievedAt`。

### 20.4 Jina Reader 读取 Roblox 搜索页

对以下 Roblox 官方搜索页使用 Jina Reader：

```text
https://www.roblox.com/discover/?Keyword=Anime%20Expeditions
```

Jina 成功读取动态搜索结果，并把 Anime Expeditions 放在第一位，同时直接返回：

- 正确 Roblox URL；
- Place ID `84515722934860`；
- Universe ID `7613921865`；
- 当前名称；
- 搜索页显示的评分和在线人数摘要。

这恰好补上了 Perplexity 通用搜索的漏检，而且基础测试无需 Jina API Key。

## 21. 对“一次 GPT 联网调用直接出结果”的判断

这条路线可以作为主要生成方式，但两个样本已经证明：**不能把一次 GPT/Perplexity 搜索结果当作唯一事实来源。**

问题不完全是模型智力，而是搜索引擎是否已经索引新 Roblox 页面。Anime Expeditions 就属于模型搜索到了大量外围资料，却漏掉最重要官方页面的案例。

为了仍然保持系统简单，当前不需要建设复杂爬虫。最小可靠流程可以是：

```text
用户只输入游戏名
→ 读取 Roblox Discover 搜索页（Jina，无 Key 可先用）
→ 选出名称最匹配的 Roblox 候选
→ Roblox 公开接口取得权威基础字段
→ 把“游戏名 + 已确认 Roblox 数据 + 原 full prompt”交给联网 GPT/Perplexity
→ 直接使用模型生成的首页结果
```

也就是说，仍然由 GPT 决定官网、社群、玩法、SEO、主题色和文案；程序只在调用 GPT 前，自动补一小段已验证的 Roblox 身份和统计上下文，防止模型研究错对象或漏掉官方页面。

### 当前默认模式建议

- Roblox 身份发现：Jina Reader 读取 Roblox Discover；
- Roblox 事实：无 Key 的公开 Roblox 读取接口；
- 联网研究和最终生成：先测试 Perplexity `fast-search`，必要时按字段补第二次搜索；
- `pro-search`：暂不设为默认，只在资料冲突/不足时使用，并提高异步超时；
- DataForSEO：当前不需要，等测试 Trailer/YouTube 字段覆盖率后再决定。

这个方案仍然只要求用户输入游戏名，不要求用户提供 Roblox URL，也不需要新增付费 API。

## 23. 联网生成 API 的候选顺序

### 23.1 首选测试：OpenAI 官方 Responses API

候选组合：

```text
OpenAI GPT-5.5
+ Responses API
+ web_search
```

把它放在首选测试位的原因：

- 用户现有基准是 ChatGPT 网页版；
- 模型和搜索工具都由 OpenAI 官方提供；
- 支持联网搜索和引用；
- 从产品能力来源看，它最接近网页版 ChatGPT 搜索。

但必须明确：ChatGPT 网页版还包含产品级系统提示词、搜索编排、界面上下文和内部配置。即使 API 使用同名模型，也不能保证结果逐字相同或质量完全一致，只能通过同 Prompt 样本测试确认接近程度。

当前尚未实测，因为工作区没有 OpenAI 官方 API Key。

### 23.2 已验证备选：Perplexity Agent API

候选组合：

```text
Perplexity Agent API
+ fast-search/pro-search
+ web_search
+ fetch_url
```

优点：

- 已经成功调用；
- 联网与引用是核心能力；
- 可以访问不同厂商模型；
- `fast-search` 延迟和成本已知。

缺点：

- 一次 fast-search 对新 Roblox 游戏可能漏掉官方游戏页；
- `pro-search` 实测出现超过 180 秒的延迟；
- 它的搜索编排与 ChatGPT 网页版不同。

因此它是可靠候选，但在完整 Prompt A/B 之前不直接宣布为最终选择。

### 23.3 OpenRouter GPT-5.5

候选组合：

```text
openai/gpt-5.5
+ openrouter:web_search
```

它可以联网，并允许选择原生、Exa、Perplexity、Firecrawl 等搜索引擎。但 OpenRouter 增加了路由和搜索工具层，距离 ChatGPT 网页版又多一层变量。

因此测试优先级暂定为：

1. OpenAI 官方 GPT-5.5 + Web Search；
2. Perplexity Agent API；
3. OpenRouter GPT-5.5 + Web Search（作为供应商/模型路由备选）。

如果用户更容易提供 OpenRouter Key，也可以把第 1 和第 3 项一起测，但不能把 OpenRouter 结果直接等同于 ChatGPT 网页版结果。

## 24. 两步实施路线

### 24.1 第一版：先复刻当前手动流程

目标是尽快证明 API 自动调用能达到可接受的手动效果：

```text
输入游戏词
→ 联网模型 API + 当前 1.1 Prompt
→ 输出 00基础信息.md
→ 图片模型生成 favicon
→ 联网模型 API + 当前 1.3 Prompt
→ 输出 00首页信息.md
```

这一版尽量保留现有 Prompt 和文档格式，只修复会导致 API 失败的硬性矛盾，不立即重写所有业务规则。

### 24.2 第二版：升级为三层架构

在第一版跑通后，将内部实现升级为：

```text
搜索/采集层
  Roblox 身份、官方数据、网页搜索、页面正文、视频候选

事实层
  字段级来源、时间戳、冲突、置信度、动态/静态标记

生成层
  Hero、SEO、模块、文案、主题色、多语言和最终文件
```

用户界面仍然只有一个游戏词输入；分层只是内部提高正确率，不增加用户操作。

这两个版本不是互相推翻：第一版建立基准和快速可用能力，第二版在不改变用户输入方式的前提下增强准确性、可追溯性和可维护性。

## 25. API A/B 测试计划

对同一个游戏、同一个完整 Prompt，保存以下三份结果：

```text
A：ChatGPT 网页版人工基准
B：OpenAI GPT-5.5 + web_search
C：Perplexity Agent API
```

如果提供 OpenRouter Key，再增加：

```text
D：OpenRouter GPT-5.5 + openrouter:web_search
```

对比指标：

- 是否定位正确 Roblox 游戏；
- 官方链接准确率；
- 字段完整度；
- 动态数据准确性；
- 是否混入竞对和第三方 Wiki；
- 是否存在虚构链接或事实；
- 引用是否真正支撑字段；
- JSON/Markdown 格式遵从；
- SEO 字符限制；
- 延迟；
- 单游戏费用；
- 结果是否可直接放入网站模板。

API 选择应以这组测试结果为依据，而不是只按模型名称判断。

## 26. OpenRouter、Perplexity、Tavily 实际对比结论

> 测试日期：2026-07-16。测试对象为 Anime Expeditions 与 PursuitCore。所有模型输入只要求从游戏名开始识别目标；用户提供的 Roblox URL 用于事后验证。

### 26.1 OpenRouter GPT-5.5 联网搜索

配置：

```text
model: openai/gpt-5.5
tool: openrouter:web_search
```

#### 身份发现结果

Anime Expeditions：

- 约 16.5 秒；
- 3 次 Web Search；
- 约 `$0.0768`；
- 准确命中 `84515722934860` 官方 Roblox 页面；
- 准确识别 Expeditions Entertainment；
- 返回 Roblox 官方引用。

PursuitCore：

- 约 96.6 秒；
- 15 次 Web Search；
- 约 `$0.5229`；
- 准确命中用户验证用的 `121903154323395`；
- 正确识别 TamaCorp；
- 发现 `84498985865861` 是旧链接并完成消歧；
- 找到 Linktree、X、YouTube、TikTok、Discord 等候选官方入口；
- 引用质量明显优于其他测试方案。

PursuitCore 的结果质量最高，但同时说明 GPT-5.5 自主搜索成本不可预测：一个看似简短的请求也可能触发 15 次搜索和约半美元费用。

#### 原完整大 Prompt

将网页端 `1.1` Prompt 原样交给 OpenRouter，非流式调用连续测试两次：

- 第一次约 156 秒后没有 `choices`；
- 第二次约 135 秒后 HTTP 200 但响应为 `null`；
- 短请求始终正常。

因此当前不能采用“把原始超长 Prompt 完全不改，单次非流式请求 OpenRouter”的实现。可能涉及长响应、上游执行或网关返回稳定性，正式实现时也应增加流式、异步、错误恢复和分段任务。

#### 分层后的精简首页请求

先提供 Roblox 已验证事实，再让 GPT-5.5 搜索社群、Trailer、兑换码和语言，并生成首页配置：

- 约 104 秒；
- 4 次 Web Search；
- 约 `$0.2475`；
- 成功返回完整内容，不再出现 `null`；
- 正确保留 Roblox URL、Place/Universe/Group ID 和动态快照；
- 能区分官方事实、第三方佐证和不确定字段；
- 主动指出代码只有第三方来源，未伪装为官方确认。

仍存在的问题：

- 输出 JSON 没有完全遵循原模板字段；
- 多语言推断中出现证据薄弱或错误引用；
- 需要 JSON Schema 和本地校验修复结构；
- 高质量搜索的成本和延迟高于 Perplexity。

当前判断：**OpenRouter GPT-5.5 是现有 Key 中质量最高、最接近 ChatGPT 网页端研究风格的候选，但应使用分层后的中等任务，而不是原始超长单调用。**

### 26.2 Perplexity Agent `fast-search`

完整 Anime Expeditions `1.1` Prompt 测试：

- 约 29.6 秒；
- 1 次 Web Search；
- 约 `$0.0257`；
- 返回了基本完整的 Markdown 和 JSON；
- 成本、速度明显优于 GPT-5.5。

但质量问题明显：

- 搜索结果已经包含正确 Roblox 游戏 URL，最终答案却说找不到 Roblox 主页；
- 没有取得可由 Roblox 接口直接获得的访问量、在线人数和收藏数；
- 要求直接下载 Hero 图时，只返回了绘图方向；
- 文案中混入中文，不完全符合英文站配置；
- 多语言选择主要依赖泛化的 Roblox 用户常识；
- 引用存在“搜到了但没有正确使用”的情况。

当前判断：**Perplexity 适合低成本搜索、候选来源和普通批处理，但不能把 `fast-search` 的完整输出未经验证直接作为最终首页配置。**

`pro-search` 仍可作为对照，但之前出现 180 秒客户端超时，不建议默认启用。

### 26.3 Tavily Search（已淘汰，仅保留测试记录）

第一次宽泛高级搜索：

- 每游戏约 5-6 秒；
- 每次 2 credits；
- Anime Expeditions 的结果严重跑偏到普通 Anime 内容；
- Tavily 的自动 answer 在来源不支撑时仍生成确定性社群描述；
- PursuitCore 找到相关视频/X/社区 Wiki，但漏掉正确 Roblox 页面并可能混入非官方 Discord。

第二次限制域名为 Roblox、YouTube、X、Discord、Linktree：

- Anime Expeditions 找到官方 Discord 和 Roblox Discover，但仍未返回直接游戏页；
- PursuitCore 成功返回正确 Roblox 页面；
- 相关度比宽泛搜索明显提高。

最终决定：**Tavily 从正式方案中移除。它不进入运行时调用链、故障降级链、配置项或后续实现任务。** 即使限制域名，其召回和事实约束仍不足以支撑本项目；本节只作为历史测试记录，避免以后重复调研。

### 26.4 网页版 ChatGPT 样本的质量观察

用户提供的 Anime Expeditions 网页版结果在内容丰富度、文案和模块规划方面优于 Perplexity fast-search，也成功定位正确 Roblox 页面。

但它并非天然可靠：

- 将发布日期、认可度和兑换码写成确定事实，其中部分仍需官方复核；
- 三条兑换码主要来自第三方页面/社区，官方 Discord 内容无法公开验证；
- 多语言优先级声称参考 Trailer 地区趋势，但没有给出足够可审计的数据；
- 首页八模块中的 Tier List 含明显的社区测试或推测；
- “可下载 Hero 横图”在保存后的 Markdown 中没有实际 URL；
- 动态数据与 Roblox 官方接口采集时间可能不一致。

因此目标应该是“达到或超过网页版的内容质量，同时增加事实可追溯性”，而不是机械复制网页版的所有结论。

## 27. 当前明确的 API 选择

在现有条件下，建议确定以下职责，而不是只选一个 API 包办全部：

```text
Roblox/Jina
  游戏身份与平台事实

OpenRouter GPT-5.5 + openrouter:web_search
  主要联网研究、疑难消歧、官方社群、最终高质量生成

Perplexity fast-search
  低成本候选来源、补充搜索、失败降级
```

如果第一版必须只选择一个“联网生成 API”，选择 **OpenRouter GPT-5.5 + `openrouter:web_search`**。原因是两个身份样本的准确率和引用质量最好，也最接近用户当前 ChatGPT 网页端使用体验。

但正式流程必须设置成本和搜索次数保护：

- 简单游戏不得无限自主搜索；
- 先注入 Roblox 已确认事实，减少模型搜索工作；
- 完整任务拆为基础事实/链接、首页 JSON、主题与语言、八模块四类任务；
- 每步缓存结果，失败只重试当前步骤；
- 对 GPT-5.5 设置单游戏预算和超时；
- 结构由 JSON Schema 与本地校验保证，不靠模型自查文字。
